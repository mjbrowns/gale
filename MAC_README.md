# macOS support

## About this change

This project modifies Gale so that it runs on macOS, in order to provide support for Valheim on macOS. It was written entirely by Claude Code, Anthropic's AI coding assistant, at the direction of the owner of this repository, who also did the hands-on testing, on one Apple silicon Mac running macOS 27. No code was copied from other projects. Treat the diff as AI-written code: section 5 says exactly what was and was not exercised.

This document describes the macOS port of Gale for review alongside the pull request, and is also the place for people running it to look up macOS-specific problems (section 7). Sections that describe changes are grouped by stage of the work (steps 1 to 4 and 6; a planned step 5, a ShaderHelperForMac hint in the UI, was dropped in favour of the troubleshooting note in section 7).

**Status.** Gale builds and starts natively on macOS (arm64, and a universal build), detects Steam games, handles deep links and opened files, and has a macOS launch path for BepInEx games. For Steam installs, which is the normal case, launching goes through Gale's existing Launcher mode, which on macOS needs a Steam launch option set by hand (section 3, step 3). That path was run end to end: a modded Valheim launch from Gale started the game, and BepInEx loaded all 79 plugins of an imported 80-mod profile with no failures; the profile was imported and updated (including BepInEx itself) through Gale's UI. Modded and vanilla launches in Direct mode from Gale also worked (section 5); a native arm64 modded launch has not been tested. Native arm64 modded launch also cannot work with released BepInEx 5 (section 6).

## 1. Summary

Gale currently builds for Windows and Linux. This branch makes it build and run natively on macOS, with modded Valheim as the acceptance test. Valheim has had a native macOS build (Steam and Mac App Store) since June 2024, and BepInEx supports it through its Doorstop run script (`DYLD_INSERT_LIBRARIES` injection) instead of the Windows `winhttp.dll` proxy.

Why native matters. Apple has announced that Intel-only apps stop launching on Apple silicon in macOS 28 (expected fall 2027), keeping only a limited Rosetta subset for older games that depend on Intel frameworks ([MacRumors](https://www.macrumors.com/2026/02/16/macos-tahoe-26-4-rosetta-2-warnings/), [9to5Mac](https://9to5mac.com/2026/02/16/macos-26-4-will-notify-users-of-rosetta-2-discontinuation/)). BepInEx plugins are IL assemblies and are architecture-neutral. The Intel dependency sits in the injection layer: the native Doorstop library shipped in the BepInEx packs, and how the game process is launched. A mod manager controls exactly that layer, so launching the injection layer natively on arm64 is the long-term technical goal. See section 6 for why that is not possible with currently released components and what this branch does about it.

A remaining Apple-silicon-specific problem is mod asset bundles whose shaders do not work on Apple silicon GPUs (pink or broken materials). The [ShaderHelperForMac](https://thunderstore.io/c/valheim/p/DrummerCraig/ShaderHelperForMac/) plugin works around it. It is an ordinary BepInEx plugin, so Gale needs no code for it: it installs like any other mod, and section 7 tells users when to reach for it.

Prior art: [Macheim](https://github.com/LovelessCodes/Macheim) is a macOS-only Valheim manager, also built on Tauri, licensed MIT. Its README says it forces an `arch -x86_64` launch path for BepInEx on Apple silicon. It was reviewed for reference only; no code is copied. A separate, older project with the same name, [lofcgi/macheim](https://github.com/lofcgi/macheim) (also MIT), makes the same statement about Rosetta.

Upstream context: the maintainer stated in [#577](https://github.com/Kesomannen/gale/issues/577) that macOS is not officially supported and that they have no Mac to test on. An earlier partial attempt, [#426](https://github.com/Kesomannen/gale/pull/426), is open and stale; it does not load mods on launch. This branch aims to keep the maintenance surface small: all macOS code is behind `cfg(target_os = "macos")` or `cfg(unix)`.

## 2. Build from source on macOS

Tested on: Apple silicon (arm64), macOS 27.0 (Darwin 27.0.0), Apple clang 21 (Xcode Command Line Tools).

Prerequisites:

- Xcode Command Line Tools: `xcode-select --install`
- Rust stable >= 1.91 (crate `rust-version`; built with 1.98.1) via [rustup](https://rustup.rs). For a universal build also run `rustup target add x86_64-apple-darwin`.
- Node.js (built with v26.10; CI uses 24) and pnpm 11.7.0 (the version CI pins). Node 25+ no longer bundles corepack, so install with `npm install -g pnpm@11.7.0`.

Commands:

```sh
pnpm install
pnpm tauri build --bundles app --config '{"bundle":{"createUpdaterArtifacts":false}}'
# -> src-tauri/target/release/bundle/macos/Gale.app
open src-tauri/target/release/bundle/macos/Gale.app

# universal app and disk image (needs both rust targets, see above)
CI=true pnpm tauri build --target universal-apple-darwin --bundles app,dmg --config '{"bundle":{"createUpdaterArtifacts":false}}'
# -> src-tauri/target/universal-apple-darwin/release/bundle/{macos/Gale.app,dmg/Gale_<version>_universal.dmg}
```

`CI=true` is set for the disk image so that the bundler's `bundle_dmg.sh` can skip the AppleScript step that styles a Finder window (its `--skip-jenkins` option). The build log does not say whether the option was applied.

The `--config` override is needed for local builds: `createUpdaterArtifacts` is `true` in `tauri.conf.json`, and building updater artifacts requires the maintainer's private signing key (`TAURI_SIGNING_PRIVATE_KEY`). Without the override the build fails at the end of bundling.

Development: `pnpm tauri dev`. Type checks: `cargo check` in `src-tauri/`, `pnpm check`.

Architecture notes:

| Target       | Command                           | Status                                                                      |
| ------------ | --------------------------------- | --------------------------------------------------------------------------- |
| arm64 (host) | as above                          | built, launches (section 5)                                                 |
| x86_64       | `--target x86_64-apple-darwin`    | compiled as part of the universal build; the slice launched under Rosetta   |
| universal    | `--target universal-apple-darwin` | built, x86_64 + arm64, signature verifies; both slices launched (section 5) |

Gale's own architecture is independent of the game's. Gale starts the game as a child process, so an arm64 Gale can launch an x86_64 (Rosetta) game.

Start the app with `open` or from Finder. Running the `.app` path directly in a terminal fails with `permission denied`, because it is a directory.

To use the build day to day, copy it to `/Applications` (`ditto <build>/Gale.app /Applications/Gale.app`, with Gale quit) and start it from there, from Spotlight or the Dock. macOS registers every `Gale.app` it sees under the same bundle identifier, including the copies left in the build folders, and `gale://` links, `.r2z` files and Spotlight can then pick any of them: a debug build and an older build were picked by mistake during testing. Keeping one copy in `/Applications` and not launching the ones under `src-tauri/target/` avoids that.

Builds are ad-hoc signed (`bundle.macOS.signingIdentity` is `-` in `tauri.conf.json`), which gives the bundle a valid seal (`codesign --verify --deep --strict` passes; without it the seal was invalid, which macOS reports as a damaged app once the file is downloaded). Ad-hoc signing is not a Developer ID: Gatekeeper still rejects the app (`spctl` says `rejected`), and a downloaded build has to be approved by the user in Privacy & Security. Setting `APPLE_SIGNING_IDENTITY` (and the notarization variables) overrides the config value per the [Tauri signing docs](https://v2.tauri.app/distribute/sign/macos/), so real signing needs no config change.

## 3. Design

Implemented (step 1, builds only):

- Every platform `cfg` that previously had only Windows and Linux arms now has a macOS arm, so the crate compiles. No Windows or Linux code path was edited apart from widening `cfg(target_os = "linux")` to `cfg(unix)` where the code is generic POSIX (shell-style argument quoting).
- macOS Steam launcher: `/Applications/Steam.app/Contents/MacOS/steam_osx -applaunch <appid>`, same argument shape as the other platforms. Game directory and launch-option lookup use the existing `steamlocate` code unchanged, which resolves `~/Library/Application Support/Steam`. Steam passed the arguments, including the profile path with spaces, through to the start script intact (`gameprocess_log.txt`). Two alternatives that avoid the macOS "modifying apps" prompt (section 6) were tried and do not work: starting Steam with `open -n -a Steam.app --args ...`, and a `steam://rungameid/<appid>//<args>` link.

Implemented (step 2, game detection):

- Game directory: no change needed. `steamlocate` resolves the Steam library under `~/Library/Application Support/Steam` (including extra library folders), so `steam_game_dir` returns the directory that contains `Valheim.app`. Only Steam installs are detected; any other install (for example the Mac App Store build, not evaluated here) can still be selected with the game-directory override in settings.
- Steam launch options: the list read from Steam's `appinfo.vdf` is not filtered by operating system. Valheim's list contains a Linux entry (`-force-glcore`) and a Windows entry (`-force-vulkan`), both meaningless on macOS. On macOS, entries whose `oslist` does not include `macos` are dropped; entries without an `oslist` are kept.
- Executable search: `find_executable` (used when a game is launched directly) takes the shallowest `.sh` or `.exe` file, and ties are decided by directory order. On the development machine the directory listing returns `start_server_bepinex.sh` before `start_game_bepinex.sh`, so the server script would be chosen. On macOS the BepInEx server script is now excluded. The same ambiguity exists on Linux; it is left unchanged there.
- Launch file copy: before every launch Gale copies the profile's top-level files into the game directory. Finder creates a hidden `.DS_Store` file in any folder it has opened, so it ended up in the game directory (Gale's log shows it being copied). On macOS it is now skipped.
- r2modman import: unchanged and not applicable. r2modman has no macOS build, so the local-install importer finds nothing and returns cleanly. Profiles reach a Mac as r2z files or profile codes exported on another platform. Zip extraction already converts backslash paths on unix (`install/fs.rs`), which such profiles rely on. Importing a Windows or Linux r2z on macOS has **not been tested**.

Implemented (step 3, launch and mod loading, Rosetta baseline):

Gale has two launch modes (`LaunchMode`): _Launcher_ (through Steam) and _Direct_ (Gale starts the game itself). Only Direct mode changed.

- Direct, modded (BepInEx): Gale runs `/usr/bin/arch -x86_64 /bin/bash <game dir>/<start script> <App>.app --doorstop-enabled true --doorstop-target-assembly <profile>/BepInEx/core/BepInEx.Preloader.dll` with the game directory as the working directory. The profile's loader files (script, `doorstop_libs/`, `.doorstop_version`, ...) are copied into the game directory before launch by the existing `copy_required_files`. Two details are required for this to work: the `.app` name must be the script's first argument, because the script's built-in default is the Linux executable name `valheim.x86_64`; and the process runs under Rosetta because the pack's Doorstop library is x86_64-only. The script is found by the existing `find_executable`; the `.app` is the first `*.app` directory in the game directory.
- Direct, vanilla: Gale runs the executable inside the app bundle (`Contents/MacOS/<App>`, falling back to the only file in that directory), with the host's architecture. Without this, `find_executable` would pick the BepInEx script left in the game directory and a "vanilla" launch would inject BepInEx.
- Direct, other mod loaders, or a game directory without an `.app`: unchanged generic behavior. Loaders other than BepInEx have not been looked at on macOS.
- Launcher mode (Steam): unchanged, and the normal path for a Steam install. `steam_osx -applaunch <appid>` appends Gale's Doorstop arguments to the game's command line, so modded launch only works if the game's Steam launch option routes the command through the start script, for example `/usr/bin/arch -x86_64 /bin/bash ./start_game_bepinex.sh %command%`. This is the same requirement as on Linux, and Gale does not set or check the option. A missing option means the game starts without mods and without an error. Gale still copies the loader files into the game directory before launching, in both modes, so the script the option points at is in place.
- Direct mode and Steam: Direct starts the game without Steam launching it. Steam has to be running, and Valheim started this way in a hand-typed test because the game directory contains `steam_appid.txt`, so the game initialised Steam's API instead of restarting itself through Steam. Games without that file may redirect to Steam when started directly (not tested). Whether Steam Cloud sync, playtime tracking and the overlay apply to a game started this way was not checked. The Direct mode setting is the per-game "Launch mode" (Platform or Direct) in Gale's settings.
- Caveats: if Rosetta is not installed, `arch -x86_64` fails after Gale has already started the process, so Gale reports success. The "launch arguments" text that Gale offers for copying (`get_launch_args`) includes the `arch` prefix arguments when Direct mode is selected.

Implemented (step 4, architecture selection):

- The Direct-mode BepInEx command from step 3 only goes through Rosetta when it has to. Gale looks for `libdoorstop*.dylib` in the game directory and in `doorstop_libs/` (BepInEx 5 packs keep it there; BepInEx 6 puts `libdoorstop.dylib` next to `run_bepinex.sh`) and reads the Mach-O header (thin or universal, no external tools) to see whether any of them has an arm64 slice.
  - x86_64-only library (current Valheim pack): `arch -x86_64 /bin/bash <script> <App>.app ...`, as in step 3.
  - A library with an arm64 slice: `/bin/bash <script> <App>.app ...`, and the script decides the architecture. Doorstop's newer `run.sh` (4.6.0) prefers arm64 and falls back to x86_64 through `arch` itself; wrapping it in `arch -x86_64` would force Rosetta.
- Gale does not check whether the BepInEx build itself works in an arm64 process. A pack that ships an arm64 Doorstop library is assumed to ship a compatible BepInEx. A mismatch (new Doorstop library with an old BepInEx 5) loads no plugins and logs nothing, see section 6. There is no setting to force Rosetta back on.
- Validated by reading real files, not by launching: the detector agrees with `lipo` on the current Valheim pack's `libdoorstop_x64.dylib` (x86_64 only, false), Doorstop 4.5.0 and 4.6.0 `libdoorstop.dylib` (universal, true), a BepInEx 6 macOS build's `libdoorstop.dylib` (universal, true), an ELF `.so` and a text file (false).

Implemented (step 6, packaging, deep links and CI):

- Deep links and opened files: Launch Services delivers `gale://` and `ror2mm://` links, and `.r2z` files opened from Finder, as open-URL events, not as `argv`, which is all `lib.rs` read. On macOS Gale now handles them in two places: `get_current()` at setup, for the link that launched the app (it arrives before any listener exists, and a first version that only registered `on_open_url` silently dropped it), and `on_open_url` for links received while running. Both call `deep_link::handle_opened`, which passes each URL to the existing `deep_link::handle`; `file://` URLs are converted to a path first because the `.r2z` handler expects a path. The runtime `register()` calls are skipped on macOS (the plugin reports `unsupported platform`); the schemes and the `r2z` document type come from the `Info.plist` that Tauri generates from `tauri.conf.json`. Windows and Linux run the same `register()` and `argv` code as before.
- Signing: `bundle.macOS.signingIdentity: "-"` (ad-hoc), see section 2. The signed build also carries the hardened-runtime flag (`flags=0x10002(adhoc,runtime)`), which Tauri enables when signing; both slices of the signed universal build were launched with it (section 5).
- CI: a `macos-latest` entry in the manually triggered `build.yaml` (`--target universal-apple-darwin --bundles app,dmg`, with both Rust targets installed on that runner). `publish.yaml` and `check.yaml` are **not changed**; the changes they would need are listed in section 6.
- Not changed: `minimumSystemVersion`. Tauri's default in the generated `Info.plist` is 10.13, which is lower than what the arm64 slice needs (11.0); it was left alone because the lowest supported version has not been tested.

Nothing is planned beyond what is listed in section 6. A ShaderHelperForMac hint in the UI was considered and dropped: the plugin installs like any mod, and Gale's Help menu has no help or troubleshooting page to hold a hint (it has three links: report a bug, Discord, About), so section 7 is the documentation for it.

## 6. Known limitations and open questions

Measured on the development machine (Valheim Steam build, BepInExPack_Valheim 5.4.2351):

- `Valheim.app/Contents/MacOS/Valheim` and its bundled dylibs are universal (x86_64 + arm64). The game is signed with a Developer ID and the hardened runtime, with the `allow-dyld-environment-variables`, `disable-library-validation` and `allow-jit` entitlements, so `DYLD_INSERT_LIBRARIES` injection is permitted.
- The BepInEx pack ships `doorstop_libs/libdoorstop_x64.dylib`, which is **x86_64 only**. Injected into an arm64 process it cannot load, so modded launch currently needs Rosetta.
- Doorstop 4.5.0 contains a universal (x86_64 + arm64) library. Native arm64 injection additionally needs a BepInEx 5 build that works inside an arm64 Unity process; the fix ([BepInEx/BepInEx#1402](https://github.com/BepInEx/BepInEx/pull/1402)) was merged to `v5-lts` on 2026-09-20 and is not in a released BepInEx (latest is 5.4.23.5) or in the Valheim pack. A native modded launch is therefore **not achievable with released components today**; whether it works once they exist is untested. Gale's side is in place (section 3, step 4) and selects the architecture from the pack's own Doorstop library.
- Doorstop's newer macOS scripts install the library next to the script rather than in `doorstop_libs/`, and the newest one changes how the injection is passed to the game (`arch -e DYLD_INSERT_LIBRARIES=...`). Gale only starts the script and passes the same first argument and Doorstop arguments as before; it was not run against those scripts.
- Valheim now reports Unity 6000.0.75f1. An open Doorstop issue ([NeighTools/UnityDoorstop#108](https://github.com/NeighTools/UnityDoorstop/issues/108)) describes hooking failures on Unity 6000.3 Mono games on Apple silicon. Valheim is on an older 6000.0 build, and whether it is affected is untested.

Open questions for the maintainer:

- **Signing, notarization, Gatekeeper.** Builds are ad-hoc signed only. A downloaded build is still rejected by Gatekeeper until the user approves it, and distributing it properly needs a Developer ID certificate and notarization, which requires credentials only the project owner can provide.
- **Updater.** The updater manifest (`latest.json` in a gist) is produced by the publish workflow from the release assets. `createUpdaterArtifacts` is on, so a macOS build with the project's updater key produces a `.app.tar.gz` and signature. Whether `tauri-action` merges a `darwin-*` entry into the same `latest.json`, and whether the gist step needs changing, has not been checked.
- **CI.** Only the manual `build.yaml` has a macOS job, and it has never run. `publish.yaml` would need the same matrix entry and Rust targets, plus a decision on artifacts (the job after the build only handles `.msi` and the AppImage hash, and the Thunderstore upload packs `.msi`); `check.yaml` runs clippy on Linux only, and macOS-gated code compiles cleanly under `-D warnings` locally. Universal versus arm64-only is left to the maintainer: the universal build works, and the x86_64 slice has not been run.
- **Deep links.** Delivery and a link-driven mod install (with its dependency and a BepInEx update) are verified (section 5). Opening an `.r2z` from Finder and the install buttons on Thunderstore and Hexium web pages are verified end to end as well. Not yet exercised: profile share links and codes, and the Discord sign-in callback.
- **Launcher-mode setup.** Launcher mode is the normal path for a Steam install, and modded launch through it depends on a launch option the user has to set by hand. Gale could read the current option from Steam's `localconfig.vdf` and warn when the start script is missing from it, which would turn a silent "no mods" outcome into a message; not implemented, to keep the change small.
- **macOS "modifying apps" notice.** macOS attributes what a process does to the app that started it. Running Steam's `steam_osx` as a child of Gale makes macOS show a notice that Gale was "prevented from modifying apps on your Mac", apparently because Steam's launcher changes its own app bundle (see the timing evidence in section 5). The game launches correctly and the mods load whether or not the notice is acted on. The developer allowed the setting once, and the next launch did not show the notice. It is expected to return whenever the app's code signature changes, since the builds are ad-hoc signed and every rebuild is a new identity to macOS; that was not verified, and a stable, properly signed and notarized release may behave differently. Both ways found to start Steam without Gale being the parent failed (`open -n`, and a `steam://` link, section 5), so this branch runs `steam_osx` directly. Direct mode does not involve Steam's launcher, with the caveats above.
- **Scope of the native-launch work.** Whether to merge launch logic that depends on an unreleased BepInEx change, or ship the Rosetta path first.
- **Relation to #426.** This branch overlaps it.

## 7. Troubleshooting (for people running Gale on macOS)

**Pink items, or particle effects such as fires drawn as blocky squares (modded Valheim on Apple silicon).**

- **Likely cause.** Many Valheim mods ship Unity asset bundles with shaders compiled only for Windows. On a Mac, Unity cannot find a variant for Metal, Apple's graphics API, and draws the material in bright pink instead. This is the explanation given in the [ShaderHelperForMac](https://thunderstore.io/c/valheim/p/DrummerCraig/ShaderHelperForMac/) README; the pink and blocky-particle symptoms were also observed by the developer on Apple silicon. It matches a limitation Unity users have described for asset bundles in general: a bundle contains shaders only for the graphics APIs of the build target it was built for, so a bundle built for Windows has none for Metal ([Unity Discussions](https://discussions.unity.com/t/assetbundles-with-shaders-for-all-standalone-platforms/747496)). The cause is in the mod's assets, not in Gale.
- **What to try.** Install ShaderHelperForMac into the profile the same way as any other mod (search for it in Gale's mod browser), then restart the game. The plugin scans the loaded mods at startup and replaces broken shaders with substitutes that render. Its README is explicit that these are a compatibility shim: textures may look flat and glow effects dimmer than the author intended, and it does not fix every mod.
- **If something is still pink.** The plugin's README describes a workflow for adding a rule for a single mod: stand next to the object, open the in-game console (F5) and run `shaderhelper nearby 15 mod` to list nearby mod materials, then run `shaderhelper patch` to write a fix rule for them. Rules are plain text files under `BepInEx/config/ShaderHelperForMac/` in the profile. See the plugin's README for the details; this is its feature, not Gale's.
- **Who is affected.** The plugin's README says it is for Apple silicon only and will not help on Windows, Linux or Intel Macs. The developer's understanding is that Intel Macs do not have the problem because the bundled x86_64 shader libraries work on them; the plugin's published README, changelog and package do not say why, so that explanation was not verified here. Whichever way the game process runs, the problem follows the Mac's hardware: the developer's Valheim runs through Rosetta on Apple silicon and needs the plugin.
- **Outlook and mod authors.** The need for the workaround should shrink as mod authors publish assets that work on Apple silicon. That is an expectation, not something verified here. The exact steps an author has to take in Unity to build such bundles (build target and graphics API settings) are not given in the plugin's published README, and were not confirmed from Unity's documentation, so they are deliberately not listed here.
- **Where this lives.** Gale's Help menu contains only a bug-report link, the Discord link and the About dialog, so this README is the only place the note exists. A maintainer who wants it in the wiki can copy the section.

**A profile imported from an `.r2z` will not launch modded: "failed to read BepInEx core directory. Is BepInEx installed?"**

- **Cause.** An import installs exactly the mods listed in the file, without their dependencies. An `.r2z` that does not list the BepInEx pack, for example one written by a tool that assumes BepInEx is already installed, therefore gives a profile with no loader. This was seen with the developer's own export tool; whether exports from r2modman or Gale list the pack was not checked here. Importing over an existing profile also removes any mod in it that the file does not list, which includes a BepInEx pack installed earlier.
- **Fix.** Install any mod, or update a mod, from Gale's UI: those installs add missing dependencies first, and the BepInEx pack is one of them. The profile's `BepInEx/core` folder is filled in when that happens. This is the same on every platform and is not changed by this branch.
